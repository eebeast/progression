01 · Three places, three responsibilities

Vercel serves the app. Your browser runs it. Supabase authenticates and stores synced records.

Vercel

Delivers application files

Vite builds JavaScript, CSS, HTML and service-worker assets. Vercel serves that build and routes deep links back to the app.

This project has no separate custom Node backend to deploy.
Your phone / laptop

Runs the application

React renders Today, Dashboard, Logbook, Plans and Settings. The repository reads and writes IndexedDB through Dexie.

Each browser/origin has its own local database. Phone storage is different from laptop storage.
Supabase

Authenticates and syncs

Google/GitHub sign-in establishes an account session. Authenticated SQL functions accept changes and return updates from PostgreSQL.

The frontend uses a public key plus the user's session. Provider secrets and database passwords stay out of the app.

Building blocks: React components · Supabase database functions. The deployed arrangement above comes from this repository.

The browser's internal route

1. React pageCollect the entered weight and reps.
2. WorkoutRepositoryThe interface every screen uses for persistence.
3. Dexie → IndexedDBSave local records in a transaction.

Read path returns: IndexedDB → observable → useObservable → React screen.

Repository means “the app's agreed way to read and save data.” Pages do not know SQL or call Dexie directly. This boundary keeps logging usable offline and makes page tests possible.

An observable is a subscription that emits new data when a relevant local query changes. That is how a saved set appears without reloading the page. Dexie liveQuery reference.

How sign-in and offline launch fit here
  1. Google/GitHub sends the sign-in result through Supabase to the app's /auth/callback.
  2. The auth client exchanges the code for a session. AccountScope selects a database named for the Supabase project/account.
  3. While signed in and online, original local history is merged into the account. Differing existing IDs are preserved/skipped; the original database remains.
  4. The service worker caches app files for later launch. IndexedDB holds workout records. They are different storage responsibilities.

A previously loaded production app can launch offline; a previously cached account can keep logging. First-time OAuth still needs a connection. This app syncs while open/resumed; it does not promise delivery while closed.

02 · A set's journey

“Saved” and “synced” happen at different moments.

  1. You press Save. The workout page calls the repository with the exercise/session IDs, 80 kg and 8 reps.
  2. A local transaction commits. The set enters logs. In account mode, the same transaction also adds an operation to outbox. Either both changes commit or neither does.
  3. The screen updates. Its observable reads local data. You can keep training without waiting for the internet.
  4. Online sync pushes the outbox. The coordinator calls sync_push. The server checks the signed-in account, record versions and references.
  5. The server acknowledges. PostgreSQL updates current records, appends a change and stores a receipt. The browser clears the accepted operation and stores the accepted version. A conflict remains pending for review.
  6. Your laptop pulls. sync_pull returns changes after its saved cursor. They enter the laptop's IndexedDB, and its screen observes the result.

An operation ID makes retrying the same request safe: its receipt returns the same outcome. A cursor is the last journal position a device has consumed. Neither is the exercise ID.

Teaching simulation only. No real browser database or Supabase account is accessed. Both devices use the same signed-in account; successful network requests are simplified to immediate acknowledgements. No conflict is simulated.

03 · Logical records versus physical tables

A set has relationships, even though its cloud payload is JSON.

Exercise “Bench Press” → reused by a Plan “Push” → started as a dated Session → contains recorded Sets.

Each set points to an exerciseId and sessionId. Repeated appearances in a plan can have their own assignment ID. New sessions snapshot their prescriptions, so later plan edits do not rewrite what was planned for that workout.

The browser has separate object stores. Supabase currently puts their entity payloads in one SQL records table, with store indicating the kind.

Kind / storeWhat it containsWhere you use it
settingsName, units, appearance, heightSettings, BMI inputs
exercisesReusable exercise ID/name; optional category, muscle and equipmentPlans, library, category lookup
templatesTraining day and ordered exercise prescriptionsPlans and Today
sessionsOne workout's date/status and prescription snapshotWorkout and Logbook
logsOne set's weight/reps or seconds, IDs, warm-up flag and orderWorkout, personal records and charts
runsDate, distance, time and optional notesToday entry, Logbook, Dashboard
bodyWeightsDate and entered weightToday entry, Logbook, BMI/chart
programOrderA cloud aggregate containing the ordered plan IDsRotation; locally represented by template order

The browser also has outbox (pending operations), versions (accepted server copies), syncMeta (cursor/status) and syncConflicts (competing edits). These support sync; they are not extra workout histories.

The actual Supabase schema

TablePurposeKey identity
auth.usersSupabase-managed account identityUser ID
workout_private.recordsLatest version of each account record, or a deletion markerUser + store + record ID
workout_private.receiptsOriginal operation request/result for safe retriesUser + operation ID
workout_private.changesOrdered changes devices pullUser + sequence
workout_private.account_stateLatest account sequence; serializes journal writesUser ID

Private workout tables have account policies and no direct browser grants. The app calls authenticated RPC functions, which derive ownership from the current session. The RPC also checks that sets/plans reference that same account's existing records.

PostgreSQL is a relational database. Our current design uses its JSONB column to preserve flexible legacy payloads. Exercise/session references inside that JSON are checked by the push function; they are not ordinary SQL foreign-key columns.

// One conceptual row in workout_private.records
user_id:    "account-123"
store:      "logs"
id:         "set-123"
version:    1
data:       {
  "id": "set-123",
  "sessionId": "session-123",
  "exerciseId": "exercise-123",
  "exerciseName": "Bench Press",
  "weight": 80,
  "reps": 8,
  "setNumber": 1,
  "timestamp": 1792483200000
}
updated_at: a database timestamp

The row's version detects competing edits. A SQL-null data value marks deletion; devices pull that tombstone instead of resurrecting an old copy.

04 · Your NULL question

The screen can calculate a label that the database never stored.

A legacy exercise can look like this:

{
  "id": "exercise-123",
  "name": "Bench Press",
  "createdAt": 1792483200000
}

What SQL sees

data->>'category' → NULL

data->>'primaryMuscle' → NULL

Neither field exists in this example. SQL reads the stored JSON; it does not execute the app's exercise-name lookup.

What the app displays

Saved category → saved muscle label → configured exercise-name/alias → fallback.

The name “Bench Press” matches the app's configured Chest preset, so Dashboard shows Chest. The pure resolver does not write that result back.

For your actual rows, inspect the raw JSON before concluding which fields are missing. SQL's extraction operator can also return NULL for a JSON-null value. See PostgreSQL JSON operators.

select id, jsonb_pretty(data) as saved_payload
from workout_private.records
where store = 'exercises' and data is not null
limit 10;

Current versus proposed: category lists/preset aliases still live in app code. The shared database catalog has been designed but not implemented. Creating a design document does not add SQL tables or backfill account records.

Similarly, height is stored in settings and weight in bodyWeights, while BMI, personal records and streaks are derived in the app. Their displayed results do not imply matching stored fields.

App evidence: category resolver. The proposed catalog migration explains how this may change later.
